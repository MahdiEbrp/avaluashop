# زیرساخت عمومی اتصال شرکت‌های حمل‌ونقل

این مرحله فقط قرارداد داخلی و Registry مستقل از ارائه‌دهنده را اضافه می‌کند. هیچ درخواست شبکه‌ای به شرکت پست، تیپاکس یا چاپار ارسال نمی‌شود و هیچ endpoint یا قالب پاسخ حدس زده نشده است.

## قرارداد مشترک

- `CarrierAddress`: مشخصات فرستنده/گیرنده با ساختار یکسان.
- `CarrierParcel`: وزن و ابعاد مرسوله و اطلاعات اختیاری ارزش/شرح.
- `CarrierQuoteRequest` و `CarrierQuote`: ورودی و خروجی نرمال‌شده استعلام هزینه.
- `CarrierShipmentRequest` و `CarrierShipment`: ثبت مرسوله و شناسه/کد رهگیری.
- `CarrierTracking`: وضعیت رهگیری و رویدادهای استاندارد.
- `ShippingCarrierAdapter`: هر ارائه‌دهنده باید سه عملیات quote، createShipment و track را پیاده‌سازی کند.
- `createShippingCarrierRegistry`: آداپترها را با کد Post، Tipax یا Chapar ثبت می‌کند و تکراری‌ها را رد می‌کند.

## افزودن ارائه‌دهنده در مرحله بعد

برای هر شرکت، آداپتر جداگانه در همین پوشه ساخته می‌شود. تبدیل مدل داخلی به payload واقعی و پاسخ واقعی فقط با مستندات رسمی همان شرکت انجام خواهد شد. خطاها باید به `CarrierAdapterError` با کد پایدار، عملیات و وضعیت retryable تبدیل شوند.

## تنظیمات و امنیت

فعلاً URL پایه، مسیرها، هدرها، API key، schema و payload provider در دیتابیس یا کد ذخیره نمی‌شوند. وقتی مستندات نهایی رسید، تنظیمات غیرحساس و credentials باید جدا نگهداری شوند؛ credentials فقط با رمزنگاری سمت سرور و از طریق پنل مدیریت وارد می‌شوند. کلیدها نباید در مرورگر، پاسخ API، log، تست fixture یا Git ظاهر شوند.

URLهای قابل تنظیم باید در زمان پیاده‌سازی allowlist/اعتبارسنجی شوند تا امکان SSRF یا درخواست به شبکه داخلی ایجاد نشود. درخواست‌های شبکه‌ای نیز باید timeout، محدودیت اندازه پاسخ، اعتبارسنجی schema و عدم دنبال‌کردن redirect به مقصدهای نامعتبر داشته باشند.

تا زمان پیاده‌سازی و تست واقعی آداپتر، روش‌های `CarrierCalculated` همچنان در checkout غیرقابل استفاده‌اند. این تغییر به‌تنهایی استعلام زنده، ثبت مرسوله یا رهگیری فعال نمی‌کند.
