# اتصال درگاه تاباپی

این پروژه از API رسمی تاباپی استفاده می‌کند؛ نه از افزونهٔ وردپرس.

## تنظیمات

پیکربندی درگاه از **دیتابیس** خوانده می‌شود، نه از متغیرهای محیطی. متغیرهای قدیمی
`TABAPAY_MERCHANT_KEY` و `TABAPAY_SANDBOX` حذف شده‌اند و دیگر خوانده نمی‌شوند.

### متغیرهای محیطی لازم

- `APP_SETTINGS_ENCRYPTION_KEY`: کلید ۳۲ بایتی برای رمزنگاری اعتبارنامه‌ها (base64 یا hex). با `openssl rand -base64 32` بسازید. **بدون این کلید هیچ اعتبارنامه‌ای ذخیره یا خوانده نمی‌شود.**
- `APP_URL`: نشانی اصلی سایت، مانند `https://avaluashop.vercel.app`.

### تنظیم از پنل مدیریت

1. `APP_SETTINGS_ENCRYPTION_KEY` را در محیط سرور تعریف کنید (پیش از هر ذخیره‌ای).
2. به `/admin/settings` بروید و کلید پذیرنده را وارد کنید.
3. حالت Sandbox را روشن نگه دارید تا آزمون‌های پرداخت کامل شوند.
4. درگاه را فعال کنید. فعال‌سازی بدون کلید معتبر پذیرفته نمی‌شود.

کلید پذیرنده با AES-256-GCM در سرور رمزنگاری و در `PaymentProvider.credentialsEncrypted`
ذخیره می‌شود. این مقدار هرگز در پاسخ API به مرورگر برنمی‌گردد؛ پنل فقط بولین
«پیکربندی‌شده» را نشان می‌دهد. اگر کلید رمزنگاری سرور عوض شود، اعتبارنامهٔ ذخیره‌شده قابل
خواندن نیست و باید از پنل دوباره وارد شود.

### ترتیب استقرار

پیش از انتشار، `npm run db:push` را روی پایگاه دادهٔ هدف اجرا کنید تا مدل `StoreSetting` و
ستون `PaymentProvider.code` ساخته شوند، سپس یک‌بار از پنل، کلید پذیرنده را ذخیره کنید. تا
زمانی که کلید ذخیره نشده باشد، درخواست پرداخت با `TABAPAY_NOT_CONFIGURED` (۵۰۳) پاسخ
می‌گیرد.

حالت Sandbox را تا پایان آزمون‌های انتها‌به‌انتها روشن نگه دارید. برای تراکنش عملیاتی، خاموش
کردن آن فقط پس از تأیید حساب پذیرندگی و تنظیمات از سوی صاحب قانونی کسب‌وکار انجام شود.

## چرخهٔ سفارش

1. سرور نشانی متعلق به کاربر، سبد، قیمت‌ها و موجودی را بررسی می‌کند.
2. سفارش با وضعیت `PendingPayment` ساخته و موجودی در همان تراکنش رزرو می‌شود.
3. سرور مبلغ ذخیره‌شده به تومان را به ریال تبدیل می‌کند و به `/v1/sandbox/create` یا `/v1/create` می‌فرستد.
4. مرورگر فقط به نشانی HTTPS معتبر متعلق به `api.tabapay.ir` هدایت می‌شود.
5. پس از بازگشت، سرور با توکن و مبلغ مورد انتظار، API تأیید تاباپی را فراخوانی می‌کند.
6. فقط پاسخ موفقِ تأییدشده با همان توکن و همان مبلغ، پرداخت و سفارش را نهایی می‌کند. callback تکراری idempotent است.
7. در پاسخ ناموفق قطعی، سفارش لغو و موجودی رزروشده بازگردانده می‌شود. خطای شبکه یا مغایرت مبلغ/توکن به‌عنوان شکست قطعی تلقی نمی‌شود و برای بررسی باقی می‌ماند.

سبد خرید تا تأیید پرداخت دست‌نخورده می‌ماند؛ هنگام موفقیت فقط تعداد اقلام خریداری‌شده از سبد کم می‌شود.

## نکات عملیاتی مهم

- API تاباپی مبلغ را به **ریال** می‌پذیرد؛ قیمت‌های فعلی فروشگاه به **تومان** نمایش داده می‌شوند، بنابراین تبدیل در سرور انجام می‌شود.
- محدودهٔ مستندشدهٔ هر تراکنش تاباپی ۱۰۰٬۰۰۰ تا ۵۰۰٬۰۰۰٬۰۰۰ ریال است.
- هزینهٔ ارسال در حال حاضر صفر است و کد تخفیف صرفاً اعتبارسنجی می‌شود؛ هنوز از مبلغ نهایی کسر نمی‌شود.
- سفارش‌های رهاشده در وضعیت انتظار پرداخت، تا زمان دریافت callback یا رسیدگی پشتیبانی، موجودی را رزرو نگه می‌دارند. پیش از بهره‌برداری واقعی باید سیاست انقضای سفارش و تطبیق تراکنش‌های بی‌پاسخ با پشتیبانی تاباپی اضافه شود.
- تغییر تنظیمات درگاه تا وقتی پرداخت در حال پردازشی در **دو ساعت** گذشته وجود دارد پذیرفته نمی‌شود. این پنجره عمدی است تا پرداخت رهاشدهٔ قدیمی‌تر، تنظیمات را برای همیشه قفل نکند.
- غیرفعال‌کردن درگاه، فقط پرداخت‌های جدید را متوقف می‌کند؛ callback و تأیید پرداخت‌های در جریان همچنان کار می‌کند.
- پس از تغییر enum در Prisma، پیش از انتشار باید `npm run db:push` روی پایگاه دادهٔ هدف اجرا و سپس `npm run db:generate` انجام شود.
- هیچ کلید مرچنت واقعی یا اطلاعات حساب بانکی را در issue، PR، فایل env نمونه یا پیام عمومی قرار ندهید.
